# OpenRhythmOD — decision & edge-case log

A static, dependency-free web rhythm game (GitHub Pages target): tap to the beat, and each tap paints in the next part of a picture-story. Good taps follow the story's good path; misses show a "fumbled" version of the same moment.

This file is the running log of decisions and edge cases. Append or update entries; mark superseded ones rather than deleting them.

---

## Decisions

### Product & scope

| # | Decision | Who | Why |
|---|---|---|---|
| D1 | Assets are **procedural first** (music synthesized in-browser, art drawn in-browser), with curated packs and free online APIs as later additions | User | Guarantees "never runs out of content" and "loads fast" with zero download and no licensing burden |
| D2 | Bad path = **shadow track**: every story beat has a good and a fumbled version of the *same* moment; the ending is chosen by final accuracy | User | The story never forks mid-song, so there are no illogical jumps between the good and bad storylines |
| D3 | The fumbled variant is a **transform, not a second asset** (re-render with perturbed parameters / a filter over the good panel) | Claude | Any art source gets bad-path art for free; hand-made bad panels would double curation forever |
| D4 | Rhythm style = **cue patterns** (call-and-response), not "tap every beat" | User | Matches the Rhythm Heaven feel the project is aiming for |
| D5 | Stack = **vanilla JS ES modules, no build step**, no external scripts or CDNs | User | Smallest payload, nothing to install, works when served as plain files from GitHub Pages |
| D6 | Milestones: **M1** procedural core → **M1.5** learnable minigames + art styles → **M2** user uploads → **M3** curated packs + online APIs | Claude | M1 exercises every hard part (clock, decode, latency) with nothing external to go wrong |
| D7 | Input = **tap + hold/release** (not tap-only, not tap+flick) | User | Adds depth without controls that are awkward on mouse or keyboard |
| D8 | Each game starts with a **short, skippable practice**, auto-skipped once that game type is cleared | User | Rhythm Heaven teaches its vocabulary before testing it |
| D9 | Progression = **level ladder + remixes** (every 4th game mixes the cues of cleared games) | User | Difficulty ramps, and remixes reward recognising learned cues |
| D10 | Art is **not limited to watercolour**: a style system (watercolour, paper cut-out, pixel, ink sketch, crayon, neon, geometric), each with its own fumble transform | User | Variety across games; styles are picked per game, weighted by minigame fit |
| D11 | Online APIs are used mainly through an **offline curation script** that commits static assets; any runtime fetching happens only on the menu screen, never during play | Claude | Runtime API calls contradict "load fast" and "never run out"; verified in-browser that Openverse works with CORS while AIC/CMA images do not |
| D12 | Uploaded files stay **local to the device** (File API only, never transmitted) | Claude | A static site has no server; this is a privacy property worth keeping explicit |

### Rhythm design (M1.5)

| # | Decision | Who | Why |
|---|---|---|---|
| D13 | Each game is **one minigame** with its own cue vocabulary, sound pack, groove and mascot | Claude, from user feedback that rhythms felt predictable with nothing to learn | The fun in Rhythm Heaven is learning one level's specific rhythms |
| D14 | Every cue sound has **exactly one meaning** within a game, and every judged event must be predictable from the audio alone — enforced by an automatic "learnability lint" | Claude | Otherwise "hard" degenerates into "unfair"; the lint keeps this true across every random seed |
| D15 | Difficulty ramps via tempo, subdivision (8ths → 16ths/triplets/swing), cue-to-response gap variety, density, fake-outs and cue combinations — **never** via events the player couldn't anticipate | Claude | "Unconventional but learnable" was the user's explicit target |
| D16 | The **player makes the response sound**: hit SFX are triggered live from pre-rendered buffers, and the baked per-note melody was removed from the song | Claude | The old song played the answer on every judged note, which removed both the challenge and the feedback |
| D17 | Song form teaches: practice → introduce cue A → vary A → introduce cue B → combine → breather → finale | Claude | Repetition is what makes a variation readable as a variation |

### Art style system (M1.5)

| # | Decision | Who | Why |
|---|---|---|---|
| D29 | Every style module exports `{ id, name, cost (1-3), renderScene(scene, rng, opts), renderFumbled(scene, rng, opts) }` from `js/story/styles/*.js`, registered in `js/story/styles/index.js` | Claude, per plan | Adding a style is a self-contained file plus one registry line; `js/story/loader.js` never branches on style name |
| D30 | Hero figures (fox/bird/boat/kite/snail/lantern) are one shared **abstract part list** (`js/story/styles/parts.js`): each part is `{role, shape: ellipse\|polygon\|dot\|path\|arc\|spiral, ...normalized coords, colorSlot}` in hero-size-normalized units | Claude, per plan | Every style walks the same list and draws each part in its own technique; a new style never needs hero-specific geometry |
| D31 | Scene composition (horizon/sun/prop/hero placement, palette-to-named-colour-slot resolution) is shared in `js/story/styles/scene.js` (`computeLayout`, `resolvePalette`), called by every style with the same rng draw order | Claude, per plan | Keeps "same seed → same composition, different rendering technique" true across styles; centralizes the fumble tilt/slump so every style gets it for free |
| D32 | `js/story/watercolor.js` + `js/story/fumble.js` were deleted; watercolour became `js/story/styles/watercolor.js` (renderScene/renderFumbled directly, no separate fumble-policy indirection) | Claude, per plan step 5 ("remove fumble.js if redundant") | Every style now owns its own fumble transform, so the old single-purpose indirection layer had no remaining callers |
| D33 | `loadStory()`'s `params` gained **optional** `stylePrefs` (style-id → weight) and `forceStyle`; `js/story/loader.js` also reads `?style=<id>` from `location.search` directly (not passed through by `main.js`) | Claude, per plan | Keeps `js/main.js`'s existing call (`{seed, numPhrases, regionCounts, lowEnd}`) working untouched while the rhythm-engine agent edits it in parallel; `?style=` is a debug override so it belongs at the source, not threaded through every caller |
| D34 | Low-end mode excludes cost-3 styles from the weighted pool **unless** a style is explicitly forced (param or `?style=`) | Claude, per plan | "Avoid the expensive ones on low-end" shouldn't silently override an explicit debug request |
| D35 | `tools/styles.html` renders every style × 3 seeds × 2 hero types (good+fumbled) plus a full-budget timing sample per style, reusing `generateStory()` + `subRng()` so it renders through the exact same code path as the real game | Claude, per plan step 6 | A contact sheet that doesn't use the real pipeline could pass while the game fails |
| D58 | **Round 2** (coordinator review): `scene.js`'s `computeLayout()` became `composeScene()` - a full shot-composition system (shot type: wide/mid/closeup/silhouette/highangle/detail; time-of-day day/golden/dusk/night; weather clear/rain/snow/fog; a far/mid/near parallax layer stack per environment type sea/forest/hills/mountains/town/path; hero third-placement, facing, near/far size) - every style now draws `composition.layers`/`celestial`/`stars`/`weatherParticles` through its OWN existing shape-fill primitive (`paintWash`/`paperShape`/`hatchFill`/`crayonFill`/`glowStroke`/`fillOutline`), so adding real scene variety didn't need bespoke per-style scenery code | Claude, per coordinator round-2 feedback ("every panel is the same postcard") | Reuses the exact pattern the M1.5 plan already established for hero parts (shared abstract shapes, per-style rendering) instead of inventing a second mechanism |
| D59 | `composeScene()`'s shot/weather/time-of-day/layer/hero-placement decisions are **independent of `opts.fumbled`** - only the hero's final pose (tilt/slump) differs | Claude | Preserves the existing "good and fumbled render the same composition" guarantee (needed for the shadow-track design, D2/D3) now that composition is much richer |
| D60 | `parts.js`'s fox and bird part lists were redrawn with much larger silhouette differences (fox: tall pointed ears, a big two-part fluffy tail, a snout bump; bird: a sharp swept-wing polygon, a long beak, a 3-feather tail fan) | Claude, per coordinator feedback ("a fox and a bird look like the same round blob") | Every style draws the same shared part list, so a bigger silhouette difference here fixes hero readability in all 7 styles at once |
| D61 | Pixel art's internal render resolution is genuinely tiny (112×~81 normal, 80×~58 low-end, vs. the previous 128/96) and the WHOLE internal frame goes through one Bayer-dither-then-quantize pass (14-colour palette) after all drawing, instead of quantizing each shape's fill colour individually | Claude, per coordinator feedback ("pixels aren't chunky enough") | A single whole-frame dither pass is what makes gradients (sky) *and* flat fills (ground/hero) all show genuine dither speckle, and is far less code than dithering every shape's fill separately |
| D62 | `tools/styles.html`'s canvases are mounted at their native rendered size (no CSS width/height downscale), with `image-rendering: pixelated` added specifically to the pixel style's canvases | Claude (bug found via coordinator's own review) | The previous contact sheet rendered pixel art at 300px and displayed it CSS-scaled to 150px, which the browser's default bilinear downscaling blurred back into a smooth gradient - the underlying bitmap was already correctly chunky, only the *preview* was lying about it |
| D63 | **Round 3**: crayon's `crayonFill` stroke COUNT is now derived from the shape's own area via a Poisson coverage model (`n = -ln(1-coverage) * boxArea / strokeArea`, capped by `maxStrokes` for perf) instead of a fixed count passed in by the caller | Claude, per coordinator feedback ("mostly WHITE with scattered coloured dashes") | A fixed stroke count doesn't scale with canvas size, so the SAME count that looked "busy" on a 150px contact-sheet thumbnail (round 2's over-correction) read as barely-there confetti at the game's real 1280px render size; deriving count from area keeps coverage % roughly constant regardless of render resolution |
| D64 | Neon's sky/grid/sun colours are now drawn from one of 4 fixed, independently-saturated `SYNTH_PRESETS` (indigo top, vivid magenta/pink/orange horizon band, bright cyan or magenta grid) picked by `paletteIdx % 4`, instead of being mixed from the story's own (often pastel) sky/accent/ground colours; a starfield is now always drawn (not gated on `composeScene`'s `tod==='night'`); a solid dark ground-plane gradient was added below the horizon (previously the sky gradient just continued there with nothing distinct); the sun was repositioned to sit low ON the horizon at 1.7x size (was in the upper-sky position `composeScene` gives every other style) | Claude, per coordinator feedback ("not reading as neon... muted olive/brown... only the hero glows") | Mixing a fixed dark colour with an arbitrary story hue can land anywhere, including muddy olive/brown when the story's palette skews warm-green; synthwave is a fixed, recognisable idiom (like watercolour or pixel art already are), so its background now has the same "always vivid regardless of story palette" guarantee pixel art's forced 14-colour palette has, while `paletteIdx` still keeps it seeded/varied story-to-story and the hero itself still uses the story's own colours (per the coordinator: "the hero glow already works") |
| D65 | Environment layers in neon are drawn as bright glow-stroke ridgelines in the grid's own hue (`drawLayerShape`), not filled+dark-stroked like round 2 - only each layer's visible top edge reads (the rest of scene.js's band polygon is off-canvas), giving a horizon silhouette-in-glow instead of the previous dim/muddy fill | Claude, per coordinator feedback ("glowing horizon ridgelines") | Matches the fix's own theme (D64): a filled-and-dimmed shape reads as muddy, a bright stroke reads as a neon tube |
| D66 | Geometric/Bauhaus no longer draws each hero part's own literal ellipse/polygon shape - every part's ROLE picks a PRIMITIVE kind (`circle`/`halfcircle`/`triangle`/`rect`) from a fixed table, and the part's own geometry only supplies where/how big to draw that primitive, oriented outward from the hero's local origin; 1-2 parts (picked by `rng.pick`, same for good/fumbled) get a small deliberate positional offset so the figure reads as overlapping primitives, not a tidy silhouette; the background grid gained a second `multiply` pass over the sky block (the `overlay` pass alone stayed faint on light backgrounds) | Claude, per coordinator feedback ("the hero is just the ordinary silhouette in flat colour... Bauhaus should abstract the hero into bold primitives") | This is the one style where "interpret the shared shape list more strongly in its own idiom" (the cross-cutting round-3 note) meant discarding the literal shape entirely, not just changing how it's filled/outlined (watercolour/papercut/ink/crayon/neon all still trace the part's own silhouette, just in different techniques) |
| D67 | **Round 4**: `js/story/loader.js` never calls `HTMLImageElement.decode()` while `document.hidden` - it waits for a `visibilitychange` to false first (`onceVisible()`), reports the wait through the existing `onProgress(fraction, label)` callback with an honest status string, and retries with a fresh `<img>` (racing `decode()` against the NEXT hide via `onceHidden()`) if the page goes hidden again before a decode settles - `decodeWhenVisible()` in `js/story/loader.js` | Claude, per coordinator's direct finding (`img.decode()` on a blob URL never resolves at all while hidden - probed directly, still pending 6s later vs. 0ms visible) | A player very plausibly taps Play and immediately backgrounds the app; the old unconditional `await warmup.decode()` hung "Painting the story..." forever with no way back. Waiting for real visibility (rather than e.g. swapping in `createImageBitmap`, which weakens the "already decoded, zero-hitch" guarantee stage.js's `<img>` reuse depends on) keeps the guarantee exactly as strong as before, just later |
| D68 | The "page went hidden" status text (`"Paused while you're away - come back to finish loading"`) is sent through `loadStory()`'s existing `onProgress` callback, not a new one | Claude | `js/main.js`'s `setProgress(frac, label)` already renders whatever string `onProgress` gives it verbatim - no change needed on the rhythm-engine agent's side of the ownership split, and the message naturally clears itself (overwritten by the next real step label) the moment loading resumes |
| D69 | **M1.6 round 1**: pixel art gets a global base weight (`BASE_WEIGHTS.pixel = 3`, `js/story/styles/index.js`) multiplied into (not replacing) each minigame's own `stylePrefs` - `weight = baseWeight(id) * (stylePrefs?.[id] ?? 1)` | User, via coordinator ("pixel ≈3x any other style, ~30-35%") | With 7 styles at base weight 1 except pixel at 3, a uniform draw lands pixel at 3/9 = 33.3% exactly inside the target band; multiplying (not overriding) means a minigame that already likes or dislikes another style still applies that preference on top, and pixel's own favouritism is never cancelled out by a style-neutral minigame |
| D70 | `quantize()`'s per-pixel nearest-colour search became a 15-bit RGB lookup table (`buildQuantizeLUT`: 32768-entry `Uint8Array`, 5 bits/channel) built once per distinct palette and cached module-wide (keyed by `` `${paletteIdx}:${mood}` ``, a single-slot cache) so it's built once and reused for every panel of a story that shares a palette | Claude, per coordinator's explicit instruction (measured 3.7-68.6ms naive at various resolutions) | A LUT read is O(1) regardless of resolution or palette size, vs. O(paletteSize) per pixel for the naive search - required *before* raising resolution, since the naive search's cost scales with pixel-count × palette-size, both of which were about to grow |
| D71 | Pixel art's internal frame grew from 112×81/80×58 to **320×~230 normal / 192×~138 low-end** (D per plan section E), and the palette grew from 14 flat colours to **26**, organised as named RAMPS (`buildRamps`: sky/ground/accent/hero/ink/paper, 3-6 shades each, dark→light) instead of a flat unordered list | User ("higher resolution, pixelated yet painterly"), Claude implementation | A flat palette can only ever produce flat colour; ramps are what let a single `colorSlot` (e.g. `'hero'`) resolve to a *range* the renderer can shade across, which flat-list quantization has no concept of |
| D72 | The hero's "volumetric" parts (`body`/`head`/`hull`/`shell` roles only) are filled with a 2-stop `canvas` `createLinearGradient` spanning the FULL ramp (index 0, its darkest shade, to the last index, its lightest) oriented toward the sun/moon (`lightDir`, computed once per render and rotated into the hero's local draw space to stay correct under pose rotation + facing flip); all other parts stay a flat single ramp shade | Claude (revised after visual review - see edge-case table) | A first attempt used only the ramp steps immediately adjacent to the part's own "base" shade (a 3-stop gradient, mid-1/mid/mid+1) and was too subtle to read at hero size once dithered/quantized - spanning the ramp's full dark/light extremes reads as a clear lit-side/shadow-side split instead |
| D73 | The small internal canvas (`small.getContext('2d', { willReadFrequently: true })`) explicitly opts into a CPU-backed (non-GPU-accelerated) 2D context | Claude, bug found via direct profiling | `getImageData()` on a GPU-backed canvas forces a GPU→CPU readback sync that dominated render time at the larger resolution (measured 9-13ms for `getImageData` ALONE at 320×230, vs. ~1.1ms for the LUT-based quantize loop it wraps) - `willReadFrequently` keeps the canvas CPU-backed from the start, since every render does exactly this readback once, by design |
| D74 | Pixel art's declared `cost` changed from 1 to **2** (still `<3`, so still eligible for the low-end style pool) | Claude, per plan section E ("the style's declared cost is re-measured after the change") | Pixel is no longer the cheapest style to render (it's mid-pack after the fixes - see edge-case table for final numbers) even though it's now clearly the most *visually* detailed; `cost` only gates the low-end pool (`<3` stays in, per D34), and keeping pixel out of the cost-3-excluded tier is essential given the user wants it favoured on low-end too |
### Rhythm engine implementation (M1.5 plan steps 1–4, this session)

| # | Decision | Who | Why |
|---|---|---|---|
| D36 | RNG is split into **four independent streams** per seed: `subRng(seed,'chart')` (songform + `game.compose()`), `subRng(seed,'synth')` (backing instrumentation + baked cue soundPacks), `subRng(seed,'sfx')` (live response soundPacks), `subRng(seed,'form')` reserved but currently folded into `'chart'` | Claude, per advisor review | Removing the old baked-melody loop deletes an `rng.int()` draw per note; on a single shared stream that would silently reshuffle every downstream value for the same seed. Independent streams make that a non-event |
| D37 | The learnability lint resolves "is this event predictable" by searching **`chart.cues` itself** for a matching `cueId` ≥1 beat earlier — never a field the composer wrote (e.g. no `predictedByCueTime` on the event) | Claude, per advisor review | A composer bug that mislabels its own predictor would otherwise grade its own homework and pass a broken chart |
| D38 | Every game's "response is predictable" pattern is unified: a priming/tell cue always sits **exactly 1 beat before** what it predicts (Balloon Pump's `pumpTick`/`tapTick`, Swing Samurai's `bonk` fake-tell, Triplet Juggle's `whoosh`/`clap`). Echo Birds and Ready-Set-Go get the same property "for free" because their call-response gap is itself ≥1 beat (or, for Ready-Set-Go's sub-beat gaps `d`, because the *first* cue is `2d` before the response, and `2d≥1` for every allowed `d`) | Claude | One mechanical rule the lint can check, instead of a special case per game. It also produced a real design improvement: fakes get a genuine advance warning (a distinct tell 1 beat early, then silence at the grid slot) rather than an unplayable same-instant reflex test |
| D39 | A hold's **release** deadline is exempt from the "cue ≥1 beat earlier" check; only its press needs one | Claude | The release time is a fixed, already-announced offset from the press (Balloon Pump's whistle rate never changes), audible for the whole hold as the baked `pump` cue itself — not a second discrete event needing its own predictor |
| D40 | Hold length (Balloon Pump) varies 1–4 beats by level, but the whistle's **pitch-rise rate is constant** across every hold | Claude | Reconciles the plan's "the rate never changes" with its "hold lengths 1–4 beats" level knob: the rate, not the length, is the fixed/learnable quantity, and it's continuously audible so a variable length doesn't break predictability |
| D41 | `js/games/echo.js` motif pools are filtered by the **current chart's tempo** (`minGap(motif) * beatDuration >= 0.125s`), and "double chirp" (which halves onset spacing) only ever draws from a separate `doubleSafe` pool whose raw gaps are all ≥1 beat | Claude (bug found via `tools/lint.html`) | 16th-note / doubled motifs that were fine at 90bpm dropped under the lint's 120ms collision minimum at 150bpm; the first `tools/lint.html` run (1686 violations) caught this immediately |
| D42 | A miss plays **no live sfx at all** (not even a soft thud) | Claude, aligning code to the plan's design principle 5 ("hitting feels good and missing is audibly silent") | The pre-rendered `response.tapMiss` buffer still exists in every soundPack (harmless, unused at play time) in case a future screen wants it; `js/main.js`'s `onJudged` just never plays it |
| D43 | Remix (`js/games/remix.js`) is special-cased in `js/songform.js buildChart()`: it calls `pickSubGames()` once per chart, then `composeSection()` (not `compose()`) per section, and every event/cue is tagged with `srcGame` so synth/sfx/mascot all key off the *originating* game, not remix itself | Claude, per plan ("each cue keeps its own sound and mascot") | Keeps remix's implementation additive — no other game module needed to change shape to support it |
| D44 | Remix's occasional 7/8 section (level 8+) is announced by a distinct unscored `oddMeter` cue at the section's start, not by the song's count-in | Claude (deviation from plan wording "announced by the count-in") | The count-in only ever precedes the whole song, not a section 40+ beats in; a per-section announce-cue satisfies "announced before it's played" without inventing a second count-in mechanism |
| D45 | Practice screen reuses the **already-rendered song buffer** (`AudioBufferSourceNode.start(when, offset, duration)` on a slice) and the real `createJudge`/`attachInput` pipeline against that section's own notes, instead of rendering separate practice-only audio | Claude | No extra OfflineAudioContext render; practice sounds and timing are byte-identical to the real game, and holds/fakes "just work" in practice for free |
| D46 | Practice material for cue type N of a game maps directly to that chart's `teachA` (N=0) / `teachB` (N=1) section | Claude | `js/songform.js`'s section-kind sequence already guarantees a `teachA` and (if the game has 2 cue types) `teachB` section exist in every chart — no separate practice-chart generation needed |
| D47 | `js/render/stage.js`'s mascot/cue-icon/pulse elements are children of `.stage__picture`, not `.stage__caption`'s sibling `.stage` container | Claude (bug found via 375px screenshot review) | `bottom:10px` on the mascot was anchoring to the whole flex column (picture + caption), so at narrow widths where the caption wraps to 2 lines the mascot corner overlapped the caption text instead of sitting in the picture's corner |
| D48 | Browser-based verification of "every game at levels 1/5/10 reaches the good/bad ending" was run for all 6 games at level 1, pump/swing/echo at all of 1/5/10 (holds/fakes/tempo-ramp being the highest-risk mechanics), the rest at 1/10, plus one remix run and 2 `?autoplay=miss` runs — not the full 6×3 events matrix | Claude, scope tradeoff | Each run plays out in real AudioContext time (~70–90s, cannot be fast-forwarded) and the pane must stay foregrounded; the learnability lint (4200 charts, <1s) is the exhaustive check, the browser matrix is a sampled realism check on top of it |
| D49 | Backgrounding mid-song (tab hidden, window blurred, or torn down for bfcache/navigation) **pauses** rather than lets the audio clock silently run ahead: `js/pause.js attachAutoPause()` listens to `visibilitychange`+`blur`+`focus`+`pagehide`, `js/main.js` stops the current `AudioBufferSourceNode` (not the whole `AudioContext` - see D50) and any live hold-sustain loops, cancels the rAF loop, detaches input, and shows a "Paused / Tap to resume" overlay | User (via coordinator), prompted by the M1.5 rAF-hidden finding | Without this, `nowCtx >= note.time + MISS_WINDOW` sweeps every note that passed while away into a `'miss'` the player never had a chance at, and `advancePhraseIfNeeded`'s catch-up loop jumps several story panels at once on return |
| D50 | Pause stops the `AudioBufferSourceNode`, not the shared `AudioContext` (`ctx.suspend()`) | Claude | The context is a page-lifetime singleton also used by calibration/menu; suspending it is more invasive for no real benefit here since stopping the source already halts all sound, and capturing `pauseCtxTime = ctx.currentTime` at the pause instant gives everything downstream needs to know "how far into the score had we gotten" without the context ever actually stopping |
| D51 | Resume requires an explicit tap (never auto-resumes on becoming visible again), which reads a fresh `resumeContext()` (satisfies the autoplay-gesture policy if the context ever did suspend for some other reason) and schedules a 4-beat count-in (live `scheduleClick`s, not baked) before a **new** `AudioBufferSourceNode` starts at `newAudioStartCtxTime` offset into the SAME pre-rendered buffer | User (via coordinator) | Matches the plan's existing count-in pattern (M1's intro click track) rather than inventing a second UI convention for "get back on the beat" |
| D52 | Resume point is always a phrase boundary - the phrase that hadn't started yet when paused if there is one, otherwise the next one (`js/songform.js planPauseResume()`) - never mid-phrase | User (via coordinator) | A phrase's cues are what make its notes predictable; resuming into the middle of one drops the player into notes with no cue context, which is exactly what the learnability lint forbids for a normal chart |
| D53 | `planPauseResume(absChart, pauseCtxTime, newAudioStartCtxTime)` is pure data - no DOM/audio - and lives in `js/songform.js`; `js/main.js`'s `pauseNow`/`resumeNow` are the only DOM/audio-touching code, and are thin glue around it plus the already-existing `stage.discardPanel`/`forceCompletePanel` and `input.js attachInput`/`detachInput` | Claude | Directly unit-testable via a plain Node import (see verification below), which is the only reliable way to check this in a harness where the pane's `document.hidden` state makes wall-clock browser verification unreliable (round 2's finding) |
| D54 | Backgrounding is disabled entirely under any `?autoplay=` mode (`pauseNow` early-returns) | Claude | `scheduleEventsAutoplay`'s synthetic pointer-event schedule is built ONCE from the chart's pre-pause note times; a time-shift partway through would desync it from the (now-shifted) chart. Autoplay is a debug/testing tool, real backgrounding is a real-player concern - they don't need to compose, and keeping them separate avoids a whole class of interaction bugs between the two |
| D55 | `js/pause.js`'s `blur` handler is **not** gated on `document.hidden` (only `pagehide` and the initial `visibilitychange` check `document.hidden`) | Claude, prompted by the task's own mobile-Safari note | On mobile Safari, `visibilitychange` can fire late relative to `blur` when switching apps; trusting `blur` unconditionally means the late `visibilitychange` just becomes a no-op re-confirmation. On desktop this also means alt-tabbing away pauses the game, which is correct behaviour for a rhythm game, not a false positive worth filtering out |

### M1.6: playability fixes (calibration, feedback, guides, practice)

| # | Decision | Who | Why |
|---|---|---|---|
| D56 | **THE root-cause fix**: calibration taps are now paired with their **nearest click by time** (`js/calibration.js pairTapsToClicks()`), never by counting position. A tap more than half a beat from every click is rejected outright rather than mis-paired | User (reported a real device playtest: zero hits in every game) | The old `clickTimes[tapCount]` indexing meant one missed/extra/early tap shifted every later pairing by a full beat (600ms @ 100BPM); the resulting offset, applied to every real tap thereafter, pushed all of them outside the ±150ms judging window forever. `?autoplay=` never caught this because it taps at exact chart times, so the same wrong offset cancels out on both sides of the subtraction - only real human input (which never lands on an exact beat multiple) exposed it |
| D57 | Calibration math (`js/calibration.js`) is a **pure module with no DOM/audio** - `pairTapsToClicks`, `computeCalibration` (MAD outlier rejection, ≥6-tap floor, ±200ms clamp-or-reject), `computeVerifyResiduals` | Claude, per plan section F ("verified by direct module import before anything else, since it blocks all real play") | Directly unit-testable via a plain Node import with zero browser dependency - this is what let the fix be verified FIRST, before any other M1.6 work, exactly as instructed. It's also what caught a SECOND real bug (D58) before that ever reached the browser |
| D58 | Self-diagnosis (`ignoredDiagnostics()` in `js/input.js`) always does the **full unconditional nearest-note scan**, never trusting `findPressCandidate`'s own "best so far" as a shortcut hint | Claude (bug found via the new `judging_e2e_test.mjs` regression test, not observed in the wild) | `findPressCandidate`'s search `break`s the instant it sees a note more than `MISS_WINDOW` ahead, WITHOUT first comparing that breaking note's own distance - so exactly at that boundary it can return a much-worse "nearest" note than the true one.
